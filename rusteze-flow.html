/ api / chat — Message Execution
What happens the moment a chat query is submitted. Every step, every function call.
1
HTTP POST /api/chat — Axum receives JSON payload main.rs:handle_chat

Axum deserializes the JSON body into a ChatRequest struct. Validation: both case_id and query must be non-empty strings — otherwise a 400-equivalent error is returned immediately.

Struct definition
#[derive(Deserialize)] struct ChatRequest { case_id: String, // e.g. "case-001" query: String, // e.g. "Is metformin appropriate here?" }
Data in flight
🌐 JSON body → ChatRequest { case_id, query } → AppState (cloned Arc)
Runtime guard — query validation
// process_chat() — chat.rs if query.len() > 100000 { tracing::error!("[Chat] ❌ INVALID QUERY: oversized string"); return "Internal error: query string is too large.".to_string(); }
⚠️ Previously the guard blocked queries >2000 chars and template strings — this caused the "Claim Evaluation Report" rejection bug. Guard now only blocks genuinely oversized strings (>100k chars).
2
QDRANT search_case_context() — Semantic RAG retrieval (case-scoped) clients/qdrant.rs

The user's query string is embedded using the BioLORD embedding sidecar (Python FastAPI, port 8000, 768-dim cosine space) — no API call to external services. The resulting vector is searched against the clinical_cases Qdrant collection with a strict case_id metadata filter to enforce patient privacy. Only chunks belonging to this specific case are returned.

Execution path
  • Initialize TextEmbedding model (BGESmallENV15) — CPU local inference
  • Embed query string → 384-dim f32 vector
  • Build Qdrant Filter::all([Condition::matches("case_id", case_id)])
  • Search clinical_cases collection — top 5 hits with HNSW (ef=128)
  • Collect payload["text"] from each hit → concatenate with --- separator
Data out
query: String → embed → [f32; 384] → HNSW → case_context: String
⚠️ On Qdrant error → case_context = "" (empty string fallback, flow continues)
3
AGENT build_grounded_context() — NER + Graph + Global Knowledge agent/prompt_builder.rs

The retrieved case chunks (not the full document) are passed through the full grounding pipeline. This adds three knowledge layers on top of the raw text: deterministic graph pathways, textbook neighborhood, and global semantic medical facts. See the prompt_builder.rs page for full internals.

Input → Output
case_context (chunks) → grounded_context: String
What's inside grounded_context
### DETERMINISTIC GRAPH PATHWAYS (Neo4j): - [Metformin] -> [INDICATED_FOR] -> [Type 2 Diabetes] ### TEXTBOOK MEDICAL KNOWLEDGE (Neo4j Neighborhood): - [Metformin] --(CONTRAINDICATED_WITH)-- [Renal Failure] ### SEMANTIC MEDICAL TRUTH (BODHI): - Metformin reduces hepatic glucose production...
4
PROMPT System prompt assembly — 3-layer context injection agent/chat.rs:process_chat

The system prompt is assembled by injecting both knowledge layers. The user's original query becomes the user message. The LLM is explicitly instructed not to hallucinate external medical history.

let system_prompt = format!( "You are a clinical AI assistant... ### PATIENT CONTEXT (Case ID: {case_id}): {case_context} ← top-5 RAG chunks ### GLOBAL KNOWLEDGE GROUNDING: {grounded_context} ← Neo4j + Qdrant global" );
5
LLM chat_with_context() — Ollama local call (main_llm) clients/ollama.rs

The assembled system prompt and user query are sent to qwen3.5:9B via the local Ollama instance (temperature 0.2, num_ctx 20480). The response is a free-text clinical answer. If the call errors, an inline error message string is returned.

API payload
{ "model": "qwen3.5:9B", // main_model from config "temperature": 0.2, "stream": false, "num_ctx": 20480, "messages": [ { "role": "system", "content": system_prompt }, { "role": "user", "content": user_query } ] }
Response
Ollama JSON → message.content → String (free text)
6
RESPONSE HTTP 200 — plain text clinical answer returned main.rs → Ok(response)

Axum's Result<String, String> return type maps Ok(response) to HTTP 200 with text/plain body, and Err(msg) to HTTP 500 with the error string. Nothing is persisted — chat is stateless.

💾 Both turns are now persisted to chat_messages in Postgres — user turn before the LLM call, assistant turn after. Logging is non-fatal (warn-only on failure).
/ api / ingest — Document Execution
Full execution path from file upload to stored adjudication report.
1
HTTP POST /api/ingest — multipart/form-data parsing main.rs:handle_ingest

Axum iterates through multipart fields. Fields named case_id are read as text. Fields named document are read as raw bytes with their filename preserved. The 50MB body limit is enforced at the router level. Empty byte arrays are silently dropped.

Field extraction loop
  • name == "case_id" → field.text() → String
  • name == "document" → field.bytes() → Vec<u8> + file_name: String
  • Empty arrays skipped. Multiple documents allowed.
🚫 Guard: if case_id.is_empty() || documents.is_empty() → return Err immediately
2
EXTRACT extract_file_text() — PDF/JSON/OCR dispatch main.rs:extract_file_text

File extension detection (lowercased filename) routes to the appropriate extractor. PDF gets a two-pass strategy — native first, then OCR fallback if the result is under 50 chars.

ExtensionStrategyFallback

3
QDRANT init_and_embed() — chunk, embed, upsert vectors clients/qdrant.rs

The aggregated text is split by \n\n (paragraph-level chunking). Each chunk is locally embedded using BGESmallENV15 and upserted into Qdrant with UUID point IDs and a payload containing text + case_id. The collection is auto-created if absent.

  • Split aggregated_text by \n\n → Vec<String> chunks
  • Batch-embed all chunks → Vec<Vec<f32>> (384-dim each)
  • Each point: { id: uuid, vector: [..], payload: {text, case_id} }
  • UpsertPointsBuilder → atomic upsert (idempotent on re-ingest)
4
POSTGRES save_case() — persist raw text record clients/postgres.rs

A row is inserted/updated in the cases table with case_id (primary key), the full aggregated text, and a timestamp. The adjudication report column is NULL at this point — it gets filled in step 6.

5
PIPELINE run_adjudication() — full Dual-Brain pipeline agent/pipeline.rs

This is the most expensive operation. It calls build_grounded_context() (NER + Neo4j + Qdrant global) and then assembles a mega-prompt combining raw document evidence with all three knowledge layers. See the pipeline.rs page for full detail.

aggregated_text → grounding → mega_prompt → heavy LLM → final_report JSON
6
POSTGRES update_case_report() + HTTP 200 with JSON verdict clients/postgres.rs → main.rs

The final_report string (JSON) is written back to the cases table. The same string is returned directly as the HTTP response body with no re-serialization.

// JSON verdict shape: { "decision": "APPROVED | REJECTED | MANUAL_REVIEW", "confidence": 0.0–1.0, "reasoning": "Detailed synthesis...", "entities_evaluated": ["Metformin", "Type 2 Diabetes"] }
↻ Retry Adjudication — POST /api/cases/:id/readjudicate

Re-runs the full Dual-Brain pipeline for an existing case without re-uploading documents. Reads document_text straight from Postgres, runs NER → Neo4j → Qdrant → LLM, and overwrites adjudication_report in-place. Useful after graph updates or model swaps.

# Re-run adjudication for case-001 curl -X POST http://localhost:3000/api/cases/case-001/readjudicate

Dispatches the document text into the full 4-stage entity resolution + Neo4j + Qdrant pipeline. Returns a pre-formatted multi-section string with three grounding layers: deterministic pathways, depth-1 neighborhood, and BODHI global semantic facts.

Also runs check_medical_necessity for every (diagnosis, drug) pair to produce graph verdicts before calling the LLM. The full context has three layers.

let full_context = format!( "### GRAPH MEDICAL NECESSITY VERDICTS:\n{graph_verdicts}\n\n ### RAW DOCUMENT EVIDENCE:\n{document_text}\n\n {grounded_context}" // Neo4j pathways + neighborhood + Qdrant BODHI );
C

Uses main_llm (qwen3.5:9B via local Ollama) with temperature: 0.1, format: json, and num_ctx: 20480. The strict JSON schema is enforced via the system prompt. On error, returns an error JSON object instead of panicking.

🛡️ Error path: {"status":"ERROR","message":"..."} — never crashes the server
agent / prompt_builder.rs
The cognitive engine: NER → 4-stage entity resolution (Postgres prefix → LLM normalize → Postgres re-sweep → BODHI Neo4j bridge) → graph pathways → BODHI global knowledge. Called by both /api/chat and /api/ingest.
1
NER extract_entities() — LLM-based named entity recognition clients/ollama.rs (ner_llm · qwen2.5:3b, temp 0.0)

The full case.document_text (not RAG chunks) is sent to the local ner_llm (qwen2.5:3b via Ollama). A hardened system prompt forces output of exactly {"medications":[],"diagnoses":[]} in JSON mode. Text is truncated to 12,000 chars. A schema-bleed guard detects adjudication keys leaking into the NER response and aborts early.

case.document_text (truncated to 12k) → qwen2.5:3b (Ollama) →
2
LINK linker::resolve_entities() — 4-stage entity resolution pipeline knowledge/linker.rs

Four cascading stages resolve raw OCR terms (e.g. "Pexime-200", "TYPHOID FEVER") into stable SNOMED concept IDs for Neo4j. Each stage feeds its unresolved misses forward. Hard failures at Stage 3 are injected as UNKNOWN_DRUG entities and still enter the BODHI bridge at Stage 4.

Stage 1 — Postgres prefix sweep (search_dictionary_prefix)

Each raw term is queried via ILIKE term% (prefix, not substring). On miss, a dash-strip fallback retries: "Pexime-200" strips "-200" → retries "Pexime%". Prefix prevents false substring matches — e.g. correctly hits Pexime (cefixime) 200mg and rejects Peximer-CR (paroxetine).

"Pexime-200" → ILIKE Pexime% → Pexime (cefixime) 200mg · snomed_id
✅ Fast hit or dash-strip hit → entity pushed to resolved list. Misses accumulate in db_misses for Stage 2.
Stage 2 — LLM normalization (normalize_terms)

All Stage 1 misses are bulk-sent to slm (qwen2.5:3b via Ollama) in one API call. Maps brand/OCR names to generic INN names. Prompt instructs: strip dose suffixes; return UNKNOWN for truly unmappable terms.

["Pantozen", "Prondem", "TYPHOID FEVER"] → qwen2.5:3b (temp 0.0) → ["Pantoprazole", "UNKNOWN", "Typhoid Fever"]
Stage 3 — Postgres re-sweep (normalized terms)

Each normalized term is re-looked up in Postgres. Terms where LLM returned "" or "UNKNOWN" are logged as Hard Fail. Diagnoses that miss the dictionary are injected as BODHI_RESCUE entries and still enter Stage 4.

⚠️ BODHI_RESCUE: vocab miss for diagnosis (e.g. "Typhoid Fever" not in NRCES dict) → injected as raw string so Stage 4 bridge still attempts Neo4j resolution.
Stage 4 — BODHI bridge (resolve_bodhi_snomed_ids)

Substance names, generic names, and rescue diagnoses are sent to Neo4j. Matched against Drug, Concept, Condition, and Symptom node labels. Returns deduplicated SNOMED IDs for fetch_deterministic_pathways.

// Stage 4 Cypher — neo4j.rs::resolve_bodhi_snomed_ids UNWIND $terms AS term OPTIONAL MATCH (d:Drug) WHERE toLower(d.name) CONTAINS toLower(term) OPTIONAL MATCH (c:Concept) WHERE toLower(c.name) CONTAINS toLower(term) OPTIONAL MATCH (cond:Condition) WHERE toLower(cond.name) CONTAINS toLower(term) OPTIONAL MATCH (s:Symptom) WHERE toLower(s.name) CONTAINS toLower(term) WITH collect(d.snomed_id) + collect(c.snomed_id) + collect(cond.snomed_id) + collect(s.snomed_id) AS all_ids UNWIND all_ids AS sid WITH sid WHERE sid IS NOT NULL RETURN DISTINCT sid LIMIT 30
🔄 Fallback: if NER returned nothing, keyword sweep scans raw document text against Postgres dictionary (words >6 chars, capped at 10 hits, lab-field tokens filtered)
3
NEO4J fetch_deterministic_pathways() — direct edges between case concepts clients/neo4j.rs

Finds directed edges where both endpoints have a snomed_id in the resolved BODHI set. Queries across all BODHI node types using snomed_id property (not id). Returns named source/target for prompt rendering.

// fetch_deterministic_pathways — neo4j.rs UNWIND $ids AS id MATCH (a)-[r]->(b) WHERE (a:Drug OR a:Concept OR a:Condition OR a:Symptom OR a:LabInvestigation) AND (b:Drug OR b:Concept OR b:Condition OR b:Symptom OR b:LabInvestigation) AND a.snomed_id IN $ids AND b.snomed_id IN $ids RETURN a.name AS from_name, type(r) AS rel, b.name AS to_name, a.snomed_id AS from_id, b.snomed_id AS to_id LIMIT 100
4
NEO4J fetch_entity_neighborhood() — depth-1 textbook context clients/neo4j.rs

Finds ALL depth-1 neighbors of any BODHI concept in the resolved set (either direction). Provides the LLM broader clinical context — comorbidities, related drugs, influencing factors. Capped at 50 results, top 15 shown in prompt. Confirmed returning 32 edges for Typhoid fever in production.

// fetch_entity_neighborhood — neo4j.rs — depth-1, bidirectional UNWIND $ids AS id MATCH (a)-[r]-(b) WHERE (a:Drug OR a:Concept OR a:Condition OR a:Symptom OR a:LabInvestigation) AND a.snomed_id = id RETURN a.name AS center_name, a.snomed_id AS center_id, type(r) AS rel, b.name AS neighbor_name, b.snomed_id AS neighbor_id, labels(b) AS neighbor_labels LIMIT 50
5
QDRANT search_global_knowledge() — BODHI semantic facts clients/qdrant.rs

Constructs query: "Medical facts regarding: <entity1>, <entity2>...". Embeds it via the BioLORD embedding sidecar (Python FastAPI, port 8000, 768-dim) and searches the bodhi_global_knowledge collection — no case_id filter. Returns top-10 facts from the payload["fact"] field (also checks "text" key for resilience). Collection currently has 9,324 points populated from Bodhi Cypher exports.

entity_names: Vec<String> → BioLORD embed → bodhi_global_knowledge (9,324 pts) → 10 medical facts
🚨 Known issue: if bodhi_global_knowledge is unpopulated the search returns 0 facts silently. Run data_scripts/seed_from_cypher.py to populate. Payload key must be "fact" (fallback: "text"). Startup log confirms: ✅ bodhi_global_knowledge has N points ready.

Comprehensive Data Schema & Tech Stack

The project leverages a "Tri-Engine" data strategy combining Relational, Graph, and Vector stores to achieve clinical grounding.

🐘 Postgres (Relational & Search)

-- Case management & Adjudication CREATE TABLE cases ( case_id TEXT PRIMARY KEY, document_text TEXT, adjudication_report JSONB, created_at TIMESTAMPTZ DEFAULT NOW() ); -- Persistent Chat History CREATE TABLE chat_messages ( id BIGSERIAL PRIMARY KEY, case_id TEXT REFERENCES cases(case_id), role TEXT, -- 'user' | 'assistant' content TEXT, created_at TIMESTAMPTZ DEFAULT NOW() ); -- Dictionary (NRCES/SNOMED Mapping) CREATE TABLE dictionary ( concept_id TEXT, snomed_id TEXT, term_type TEXT, name TEXT, substance_name TEXT, generic_name TEXT, indication TEXT, interaction_with_drugs TEXT );

🕸️ Neo4j (BODHI Graph)

// Node Labels - (:Drug) {snomed_id, name, synonyms} - (:Concept) {snomed_id, name, display_name} - (:Condition) {snomed_id, name} - (:Symptom) {snomed_id, name} - (:LabInvestigation) {snomed_id, name} // Relationships - [:IMPACTS] (Drug → Concept) - [:INDICATED_FOR] (Drug → Condition) - [:CONTRAINDICATED_WITH] (Drug → Condition) - [:HAS_SYMPTOM] (Condition → Symptom)

🧿 Qdrant (BODHI Vector)

// Collection: clinical_cases (Local RAG) - Payload: { "text": string, "case_id": string } - Index: Cosine, 768-dim (BioLord) // Collection: bodhi_global_knowledge (Global RAG) - Payload: { "fact": string } - Index: Cosine, 768-dim (BioLord)

🛠️ Technology Stack

  • Backend: Rust 1.75+ (Axum, Tokio)
  • Databases: Postgres (deadpool), Neo4j (neo4rs), Qdrant
  • Embedding: BioLord (768-dim) via local/remote encoder
  • LLMs: Tri-Brain (Main: Qwen 9B, SLM: Qwen 3B, NER: Qwen 3B)
  • Grounding: Dual-Brain GraphRAG (Grounding + Pathways)
